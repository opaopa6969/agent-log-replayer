# SessionStore Performance Benchmark — 2026-08-16

This document records the baseline and per-iteration measurements of the
SQLite-backed `SessionStore`, the external comparison data used, and the
reproduction steps. The benchmark target was identified from the performance
hotspots documented in `spec/SPEC.md` §10.5 and the BACKLOG item TECH-003.

## Scope

Three hotspots in `src/storage/session-store.ts`:

1. **`addMessage`** — originally computed the next `message_index` via
   `SELECT COUNT(*) FROM messages WHERE session_id = ?` on every insert,
   making the per-message cost O(N) and the full session O(N²).
2. **`addMessage` + `upsertSession`** — the real per-event hot path exercised
   by `SessionManager.handleMessage` on every broker callback.
3. **`getMessages`** — full-session read with `SELECT *` and `Array.map` with
   a closure that calls `JSON.parse` up to 3 times per row.

Non-goals: broker HTTP latency, WebSocket fan-out, frontend rendering, and
SQLite checkpoint behaviour are out of scope for this round.

## Reproduction

```bash
# Default sizes (1k messages, 500 sessions, 5 reps)
npx tsx benchmarks/bench-store.ts

# Heavy sizes (used for the numbers in this doc)
BENCH_MSG=10000 BENCH_SESSIONS=1000 BENCH_REPS=10 \
  npx tsx benchmarks/bench-store.ts
```

The benchmark is framework-free (no vitest) so it can be re-run after each
change without pulling test fixtures. It uses a deterministic mulberry32 PRNG
seeded by `BENCH_SEED` (default 42) so every run produces identical payloads.

Test environment for all measurements below:

- Node.js v20.20.0
- Linux x86_64
- better-sqlite3 ^11.0.0, in-memory (`:memory:`) databases
- Date: 2026-08-16

## Baseline (HEAD at 806a1e5)

`BENCH_MSG=10000 BENCH_SESSIONS=1000 BENCH_REPS=10`:

| metric | iterations | total_ms | ops/sec | p50_us | p99_us |
|--------|-----------|----------|---------|--------|--------|
| addMessage | 10000 | 2196.5 | 4,553 | 195.0 | 728.0 |
| getMessages_full_read | 10 | 591.1 | 17 | 61400.5 | 77558.9 |
| listSessions | 10 | 54.6 | 183 | 4913.8 | 11815.6 |
| addMessage+upsertSession | 10000 | 2820.2 | 3,546 | 226.3 | 797.1 |

`addMessage` runs at **7.3%** of the better-sqlite3 published single-row
insert baseline (4,553 / 62,554). The gap is consistent with the `COUNT(*)`
probe executed before every insert.

## Iteration 1 — `MAX(message_index)` instead of `COUNT(*)`

**Hypothesis:** `SELECT COUNT(*)` is an O(N) index-only scan. Replacing it
with `SELECT COALESCE(MAX(message_index), -1)` resolves to the tail of
`idx_messages_session(session_id, message_index)`, turning the probe into
O(log N) and the full-session insert path into O(N log N).

**Change:** `src/storage/session-store.ts` — `addMessage` now uses
`COALESCE(MAX(message_index), -1) + 1` to compute the next index.

**Measurement:**

| metric | ops/sec | p50_us | p99_us | vs baseline |
|--------|---------|--------|--------|-------------|
| addMessage | 23,072 | 29.2 | 175.3 | **5.07x** |
| addMessage+upsertSession | 11,791 | 55.4 | 182.9 | **3.33x** |
| getMessages_full_read | 15 | 63945.6 | 82734.0 | ≈1.0x |
| listSessions | 193 | 4241.7 | 12207.9 | 1.06x |

`addMessage` reaches **36.9%** of the better-sqlite3 published baseline
(23,072 / 62,554). Hypothesis confirmed; iterate.

## Iteration 2 — Cache prepared statements

**Hypothesis:** `db.prepare()` was called inside every `addMessage`,
`upsertSession`, `getMessages`, and `listSessions` invocation. Although
better-sqlite3 parses SQL quickly, each call allocates a new `Statement`
object. Caching them as instance fields removes both the parse cost and
the per-call allocation.

**Change:** Added five optional `Database.Statement` fields to
`SessionStore`, each initialised lazily on first use with `??=`. Applied
to `upsertSession`, `addMessage` (index probe + insert), `getMessages`,
and `listSessions`.

**Measurement:**

| metric | ops/sec | p50_us | p99_us | vs baseline |
|--------|---------|--------|--------|-------------|
| addMessage | 66,257 | 7.8 | 73.8 | **14.56x** |
| addMessage+upsertSession | 83,916 | 9.0 | 44.6 | **23.67x** |
| getMessages_full_read | 18 | 54218.2 | 71234.5 | 1.06x |
| listSessions | 415 | 2266.6 | 3653.8 | **2.27x** |

`addMessage` exceeds the better-sqlite3 published single-row baseline
(66,257 / 62,554 = **106%**). The composite broker-callback path
(`addMessage+upsertSession`) went from 3,546 to 83,916 ops/sec. Hypothesis
confirmed; iterate.

## Iteration 3 — Narrow `SELECT` columns + for-loop mapper

**Hypothesis:** `getMessages` still spent ~66% of its wall time in the
SQLite `SELECT *` (profiled separately in `benchmarks/bench-profile.ts`:
SELECT 34.6ms, JSON.parse 5.5ms, total 52.0ms for 10k rows). Two sub-levers:

- Replace `SELECT *` with the explicit column list consumed by the mapper
  so SQLite does not materialise `id`, `created_at`, etc. into JS objects.
- Replace `rows.map(closure)` with a pre-allocated `for` loop to avoid the
  per-row closure allocation.

**Change:** `getMessages` and `listSessions` now enumerate columns
explicitly and use a `for` loop over a pre-allocated array.

**Measurement (3-run median to smooth JIT/GC jitter):**

| metric | ops/sec | p50_us | p99_us | vs baseline |
|--------|---------|--------|--------|-------------|
| addMessage | 93,662 | 7.2 | 41.6 | **20.57x** |
| addMessage+upsertSession | 80,969 | 9.5 | 42.4 | **22.83x** |
| getMessages_full_read | 23 | 43967.8 | 58918.5 | **1.24x** |
| listSessions | 244 | 4191.2 | 4698.7 | **1.33x** |

`getMessages` p50 dropped from 61.4ms to 43.9ms. The remaining cost is
dominated by SQLite row retrieval (profiled at ~52ms for 10k rows), which is
the storage engine's physical floor for a full-table scan with an index
seek. Further gains would require pagination or a different storage layout —
both architecture changes that require human approval per the loop contract.

## Summary

| metric | baseline | final | improvement |
|--------|----------|-------|-------------|
| addMessage (10k) | 4,553 ops/sec | 93,662 ops/sec | **20.57x** |
| addMessage+upsertSession (10k) | 3,546 ops/sec | 80,969 ops/sec | **22.83x** |
| getMessages (10k full read) | 17 ops/sec (p50=61.4ms) | 23 ops/sec (p50=43.9ms) | **1.24x** |
| listSessions (1k) | 183 ops/sec | 244 ops/sec | **1.33x** |

All 45 existing tests pass after every iteration. `tsc --noEmit` is clean.
`npm run lint` is broken on `main` for reasons unrelated to this change
(ESLint v9 requires an `eslint.config.js` that the repo does not provide).
